# 答辩演示脚本

> 建议时长：8—10 分钟
> 演示地址：<http://localhost:8080>
> 演示目标：让评委在最短时间内看到“简历 → 诊断 → 面试 → 成长”的完整闭环，以及规则与模型的分工。

## 1. 演示前检查（提前 10 分钟）

```bash
docker compose --env-file .env.docker ps
curl -s http://127.0.0.1:8080/api/v1/health
```

- `db`、`api`、`web` 均为 `healthy`，健康检查返回 `status=ok`。
- 已登录一个演示账号，浏览器缩放 100%，关闭无关标签页与通知。
- 准备好一份 PDF/DOCX 简历（建议 1 页，含教育、工作、项目、技能）。
- 准备好一个目标岗位（必备技能、加分技能、关键词、职责、任职资格）。
- 若模型响应慢，提前创建一份诊断和一场面试作为兜底。
- 录屏备份：完整流程录一次，防止现场网络或模型异常。

## 2. 演示流程

### 0:00—0:40 开场与架构

操作：打开工作台首页。

讲解：

> 这是一个基于 DeepSeek 的简历诊断与面试模拟平台。前端 Vue 3，后端 FastAPI + PostgreSQL 17，模型只负责语义判断，分数由程序按固定权重复现。整套系统用 Docker Compose 部署，三个容器都带健康检查。

要点：不要一开始讲技术细节，先给闭环：**上传 → 结构化 → 诊断 → 面试 → 成长**。

### 0:40—1:30 登录与工作台

操作：登录，展示工作台的四维权重与开发路线。

讲解：

> 账号体系使用 Argon2 密码哈希与 JWT，所有简历、诊断、面试数据按用户隔离。

### 1:30—3:20 上传与结构化解析

操作：

1. 进入“简历”，拖入准备好的 PDF/DOCX。
2. 等待状态变为“已提取”，点击“结构化”。
3. 点击“用 DeepSeek 解析”，等待 10—20 秒。
4. 展开教育、工作、项目、技能，指出每条记录都有原文来源。

讲解：

> 原文件落盘到按用户和简历 ID 隔离的目录，文本提取用 PyMuPDF 和 python-docx。结构化只使用简历事实，每条经历保留 `source_text`，后续诊断和面试都能追溯。

可指出的验收点：

- 字段包含姓名、联系方式、教育、工作、项目、技能、证书。
- 模型输出经过 Pydantic 校验，失败会重试一次。
- 解析结果保存为 v1，后续人工修改生成 v2，不覆盖 v1。

### 3:20—4:00 人工校正

操作：修改一处摘要或补一条技能，保存为新版本，展示版本历史。

讲解：

> 模型不可能 100% 准确，所以设计了人工校正与版本管理。诊断和面试都绑定具体版本，历史记录不会被覆盖。

### 4:00—6:00 岗位与四维诊断

操作：

1. 进入“岗位”，展示必备/加分技能、关键词、职责、任职资格。
2. 回到结构化页，点击“开始诊断”，选择版本与岗位。
3. 展示总分、四维分数、雷达图。
4. 切到“关键词”，指出命中与缺失。
5. 切到“JD 匹配”，指出逐条证据。
6. 切到“修改示例”，指出“需补充事实”标记。

讲解：

> 四维权重固定：格式 15%、完整度 20%、关键词 25%、JD 匹配 40%。格式、完整度、关键词由规则计算；模型只对 JD 要求逐条判断 met/partial/missing 并给出原文证据，总分由程序合成。修改示例如果新增了原文没有的数字，会自动降级为“需补充事实”，防止编造。

### 6:00—8:30 模拟面试

操作：

1. 进入“面试”，选择简历版本、岗位、综合面试，生成 8 道题。
2. 展示题目来源标签：简历 / 岗位 / 行为题。
3. 回答第 1 题，等待评价。
4. 展示五维评分与追问，回答追问。
5. 点击“结束面试”，生成复盘报告。
6. 展示报告中的优势、短板、改进建议与逐题点评。

讲解：

> 出题必须标记来源，来源无法在简历或 JD 中核实时会降级为通用行为题。评价五维：相关性、专业正确性、结构、证据、表达，等权平均为单题分。追问最多两级，插在父题之后。结束只做确定性汇总，报告单独生成，失败可以重试。

时间不够时：只答 2 题就结束，重点展示“评价 + 追问 + 报告”，不要逐题念。

### 8:30—9:30 成长分析

操作：进入“成长”，切换简历范围，展示诊断/面试趋势、五维变化、弱项聚合。

讲解：

> 趋势只在同简历、同岗位、同 `rubric_version` 下比较，面试还要求同类型，不同口径不混算。弱项来自诊断缺失关键词、未满足要求和面试低分维度。

### 9:30—10:00 收尾

讲解：

> 系统已经容器化部署，数据库迁移在 api 启动时自动执行，上传文件与数据库都用命名卷持久化。当前验证了 126 项后端测试、45 项前端测试，以及三容器健康检查和经 Nginx 的注册/上传链路。下一步会补真实模型在诊断与面试上的质量评估。

## 3. 演示数据建议

| 数据 | 建议 |
|---|---|
| 简历 | 1 页中文简历，含 1 段工作、1—2 个项目、技能分组 |
| 岗位 | 后端开发工程师，必备 Python/Docker，加分 FastAPI，关键词 PostgreSQL |
| 诊断 | 提前跑一次，确认总分与修改示例正常 |
| 面试 | 提前生成一场，至少答 2 题，确认报告可生成 |
| 账号 | 专用演示账号，避免现场注册耗时 |

## 4. 异常兜底

| 情况 | 处理 |
|---|---|
| 模型响应慢 | 继续讲架构与规则，或直接打开预生成的诊断/面试记录 |
| 模型 502/503 | 说明服务端有明确错误码与重试；切到预生成记录继续 |
| 上传失败 | 检查文件类型与 10MB 限制，换备用 PDF |
| 页面异常 | 刷新；仍异常则播放录屏，不要现场排查 |
| 网络中断 | 使用本地部署与录屏；不要依赖公网演示 |

## 5. 常见提问与回答

**为什么不用大模型直接打分？**

> 纯模型打分不可复现，同一份简历两次可能不同，也无法解释。这里让规则算分、模型给证据，总分由程序合成，才能支持历史对比和答辩解释。

**如何防止模型编造经历？**

> 三层约束：Prompt 禁止新增事实；每条经历保存原文 `source_text`；程序校验原文摘录，改写新增数字自动降级为“需补充事实”。

**为什么选 PostgreSQL？**

> 简历、诊断、面试大量使用 JSONB；同时需要事务、索引和 Alembic 迁移。SQLite 与生产环境差异太大，所以明确禁止。

**为什么不用 Redis？**

> MVP 没有队列、缓存和分布式会话的硬需求；JWT 无状态，统计直接查 PostgreSQL。引入 Redis 会增加部署与一致性成本。

**历史分数为什么可以比？**

> 诊断按简历 + 岗位 + `rubric_version` 分组，面试再增加面试类型；同时保存 `prompt_version` 和模型名。不同口径不混算。

**追问会不会无限递归？**

> 不会。追问层级最多两级，服务端强制校验；追问插入父题之后，题目顺序自动后移。

**模型超时或限流怎么办？**

> Provider 对 429/5xx 和网络异常做指数退避重试，4xx 不重试；业务层返回 502/503，不保存半成品数据，用户可以重试。

**数据安全怎么保证？**

> 密码 Argon2，JWT 鉴权，所有查询带 `user_id`；文件按 UUID 目录隔离；密钥只在服务端环境变量，`.env` 不提交。

**项目最大的不足？**

> 真实模型质量还需要更多样本评估；图片简历未接 OCR；诊断和面试是同步调用，长文本可能超时；这些都是下一步工作。

## 6. 一句话总结

> 这个系统的核心不是“让大模型写简历”，而是把简历、岗位、诊断、面试和成长记录变成**可追溯、可复现、可比较**的数据链路。
